# MDP Connect — resident introductions

Implemented locally on web and native: public-area journey offers, pickup/destination text filters, discovery/connections/offers views, explicit resident requests, driver acceptance, atomic seat allocation, withdrawal, reporting and blocking. Web also filters by journey date in IST. Contact sharing is separate from social profiles and opt-in per journey. No contact is seeded or copied from resident profiles. Each side can choose independently to share or remove their own phone number; only accepted eligible participants can retrieve the counterpart's shared number. Sharing on an offer consents to visibility to all accepted participants on that offer; passengers cannot retrieve other passengers' contacts.

No fare entry, carpool gateway, commission, in-app carpool chat, GPS or road-route ranking. Existing contribution columns are legacy storage; new offers store zero and discovery responses omit them. Public meeting areas must not contain flat addresses. Verification badges explicitly identify demo residents.

Requests can be withdrawn exactly once; accepted withdrawals restore a seat and remove passenger contact consent. Blocking cancels pending/accepted connections between the pair and restores accepted seats. Server discovery and actions check bilateral blocks and current eligibility. Cancelled/expired rides cannot return contacts. Removing consent cannot retract phone numbers already saved by another person.

API: POST /api/rides creates an offer; PATCH /api/rides/:id supports request, accept, reject, cancel, withdraw, share_contact, report, block. Reports use existing moderation records. Contact strings allow optional + and 10–15 digits and are never put in audit logs. No contact payload is included in request or acceptance; a separate share_contact operation records the explicit choice.

This remains the localhost-only SQLite demo. Contacts are private application records in the local database, not a production encrypted contact service. The existing Supabase foundations are not connected to these flows; production requires audited migrations/RPCs, authorisation and revocation handling, OTP/real membership verification, abuse limits, retention/cleanup and consent notices. True road-route matching requires coordinates, spatial indexes and routing integration. Native type validation is automated; physical device UI and store release are unverified.
